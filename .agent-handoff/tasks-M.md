## Goal
Every movement should feel like one physical system: content follows the finger 1:1, releases continue with the finger's velocity, nothing animates twice, nothing jumps, and every transition tells the user where they went (direction = tab order). 60 fps on iPhone (WKWebView). Respect `prefers-reduced-motion` (replace motion with ≤120 ms opacity crossfades, never remove feedback entirely).

## Diagnosis (Claude, verified in source — fix these)
1. **Two different tab transitions.** Tap on a tab → `go()` → `render()` → `#view.v-in` "rise" (fade + 8px up). Swipe → horizontal slide. Taps must use the same directional slide as swipes.
2. **Double animation after swipe.** `finishSwipe` slides view+preview, then calls `go(next)` which re-renders and replays `v-in` rise (and first-visit `.stagger`, number count-ups, bar fills). After a swipe/tap slide, the incoming content must land already settled: no rise, no stagger, no count-up replay on the frame after the slide ends (count-ups/bars may run once, only on a tab's very first visit, and must start *while* the slide is running, not after).
3. **Release ignores velocity.** Swipe commit/cancel always runs a fixed 220/240 ms curve regardless of remaining distance and finger speed; velocity is the average since touchstart, not the recent velocity. Use the velocity over the last ~80 ms (keep a short sample buffer), project the end (`x + v * 0.2s`-style projection) to decide commit vs cancel, and derive duration from remaining distance/velocity (clamp ~180–380 ms) with an ease-out/spring curve so the hand-off from finger to animation has no speed discontinuity.
4. **Tab indicator.** Final CSS rule `.tabs::before { … transition: transform 80ms linear }` (proto.css ~line 865) overrides the spring. During finger drag (tabbar drag or content swipe) the pill must track 1:1 with no transition; on release/tap it must glide with the spring (`--ease-spring`, ~320–360 ms). The `setTimeout(… removeProperty("--tab-i"), 360)` hand-back must not cause a visible snap or second movement.
5. **Edge rubber-band.** At first/last tab the drag uses a linear `dx * .28`. Use a proper diminishing rubber-band (e.g. `d * c / (d + c)` style, c ≈ 0.35·width) and spring back.
6. **Conflicting duplicate motion rules.** Press states (`:active` scale) and `button/summary/a` transitions are defined 3+ times with different durations/curves (≈ lines 693–695 vs 870–875); `.sheet` keyframe animations are declared then disabled (`animation:none`) while the real ones live in JS; `.tabs::before` width/transform declared 3 times. Consolidate to one coherent set of motion tokens (`--dur-1..4`, `--ease-out`, `--ease-spring`, `--ease-in`) and one rule per behaviour. Delete dead rules. Do not change non-motion styling.
7. **Sheets.** Open/close are fine in principle; make them match the system: drag-to-dismiss must use recent velocity (same helper as swipes), allow drag from the whole sheet when its body is scrolled to top (not only the header), rubber-band when dragging up past open, closing duration derived from remaining distance/velocity, scrim opacity tied to drag progress, and the background page gets a subtle scale/dim (iOS card style, ≤ 0.96 scale on mobile only) that tracks the sheet. Opening a sheet from a tap must start within one frame.
8. **Scroll restoration on tab change** must happen before the incoming content becomes visible (no jump after the slide). The swipe preview must show the target tab at its saved scroll position, so the frame after commit is identical to the last frame of the slide (no pop).
